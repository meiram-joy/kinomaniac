# Киноманьяк

Программа подбирает фильм под сложный запрос («фильм как Интерстеллар, но не про космос», «что посмотреть с мамой на казахском, до двух часов») и советует **только фильмы из своего каталога**. Модель видит каталог и называет фильмы по id, код сверяет каждый id с каталогом, а название, год, длительность и описание печатает из каталога.

**Достигнутые уровни:** Common, Rare, Epic.

## Запуск

Нужны [uv](https://docs.astral.sh/uv/) и [Ollama](https://ollama.com) с моделью `qwen3.5:4b`.

```bash
uv sync
ollama pull qwen3.5:4b
```

**Важно: Ollama нужно запускать с контекстом больше стандартного.** Каталог в промпте занимает около 6 200 токенов, а по умолчанию Ollama держит окно 4 096 и молча отрезает начало промпта (в логе сервера: `truncating input prompt limit=2050 prompt=6257`). Тогда модель не видит часть каталога, в том числе казахстанские фильмы.

```bash
# Linux / macOS
OLLAMA_CONTEXT_LENGTH=16384 ollama serve
# Windows PowerShell
$env:OLLAMA_CONTEXT_LENGTH=16384; ollama serve
```

Команды проекта:

```bash
uv run kino.py "фильм как Интерстеллар, но не про космос"   # один подбор
uv run check.py                  # прогон набора queries.json
uv run check.py --runs 3 --model qwen2.5:14b   # другая модель, 3 прогона
uv run show.py                   # журнал: исходы, токены, цена
uv run pytest                    # тесты с заглушкой, без модели и сети
uv run tools/memory_test.py      # опыт с памятью модели
uv run tools/fetch_big.py        # Epic: собрать films_big.json
uv run tools/big_check.py recall           # Epic: попал ли must в 30 кандидатов (без модели)
uv run tools/big_check.py size            # Epic: размер всего каталога в токенах (без модели)
uv run tools/big_check.py path --limit 10  # Epic: кандидаты против всего каталога в промпте
```

Для замера «весь каталог в промпте» (Epic) нужно окно около 190 тысяч токенов: `OLLAMA_CONTEXT_LENGTH=196608 ollama serve` (`qwen3.5:4b` держит до 262 144).

Без ключа API: всё работает на локальной модели. Для облачной модели: `KINO_MODEL`, `KINO_BASE_URL` и `OPENAI_API_KEY` в `.env` (образец — `.env.example`) или в окружении.

## Как устроено

```
kino.py            pick и pick_big, чтение каталога из файла, клиент модели, запуск из командной строки
kinomaniac/
  catalog.py       модель Фильма, словарь жанров, проверка каталога
  schema.py        схема ответа модели: status, reason, picks (film_id, why)
  prompt.py        инструкция и данные в тегах <каталог> и <запрос>
  verify.py        проверка ответа кодом: чужие id, повторы, не больше трёх
  filters.py       Rare: схема Filters, отбор каталога и проверка фильма по условиям
  search.py        Epic: candidates() — отбор 30 кандидатов без модели (правила + TF-IDF)
  llm.py           вызов модели, все сбои -> исход
  journal.py       строка в calls.jsonl на каждый вызов, чтение журнала, цена
  render.py        печать фильмов и сообщений
check.py, show.py, tests/, tools/
```

Модули `catalog`, `schema`, `prompt`, `verify`, `filters`, `search` не обращаются к сети и файлам и ничего не печатают, поэтому их легко проверять. Ввод-вывод — в `llm`, `journal`, `render` и `kino.py`. `pick` только соединяет шаги:

1. **фильтры** (`step: filters`): модель разбирает запрос в схему `Filters`;
2. код отбирает из каталога фильмы, подходящие под условия;
3. **выбор** (`step: choice`): модель выбирает среди отобранных;
4. код сверяет id с каталогом и ещё раз проверяет каждый фильм по условиям;
5. печать и журнал.

Исходы: `ok`, `no_match`, `invalid`, `refusal`, `length`, `no_connection`, `error_<код>`. Фильмы показываются только при `ok`.

## Каталог

`films.json`: **47 фильмов, из них 12 казахстанских** (казахстанские, советские, фантастика, комедии, ужасы, семейные, мультфильмы, документальные).

- **Источник года и длительности — [Wikidata](https://www.wikidata.org)** (свойства P577 «дата публикации» и P2047 «продолжительность»; год — самая ранняя дата, потому что у фильмов бывают премьеры в разных странах и перевыпуски). Жанры, страны и языки — тоже из Wikidata, жанры приведены к словарю каталога. Описания кратко пересказаны по разделу «Сюжет» статей русской Википедии. Wikidata распространяется под CC0, тексты Википедии — под CC BY-SA.
- Каталог собирает скрипт `tools/fetch_wikidata.py` (SPARQL-запросы, `build` → `tools/films_draft.json`, `finalize` → `films.json`). Q-id каждого фильма для сверки лежит в `tools/films_draft.json`.
- Жанры, языки и страны Wikidata приводятся к словам каталога таблицами в коде (`GENRES`, `LANGUAGES`, `COUNTRIES` в `tools/fetch_wikidata.py`: «драматический фильм» → «драма», «путунхуа» → «китайский», «Республика Корея» → «Южная Корея»).
- Жанры в Wikidata оказались грязными (у «Однажды в Америке» стояли «документальный» и «вестерн»), поэтому явные ошибки исправлены в `GENRE_OVERRIDES`, а два фильма исключены в `EXCLUDE` с причиной.

## Пять вопросов лекции 1

1. **Цель.** Человек описывает желаемый фильм обычной фразой и получает 1–3 фильма, которые действительно существуют, с верными годом и длительностью, или честное «ничего нет».
2. **Решение без ML.** Фильтр по полям каталога: жанр, язык, страна, длительность, год, плюс поиск по ключевым словам в описании.
3. **Данные.** Каталог из 47 фильмов (Wikidata + Википедия) и набор из 30 запросов с ожиданиями (`queries.json`; первые 16 — набор уровня Common).
4. **Что выдаёт программа.** До трёх фильмов из каталога: название, год, длительность и описание из каталога и одна причина от модели. Либо сообщение: «ничего нет», «модель ответила некорректно», «нет связи» и т. д.
5. **Цена ошибки.** Если показать несуществующий фильм или неверный год, человек потратит время на поиски или разочаруется, и программе перестанут доверять. Поэтому ответ «ничего нет» лучше, чем выдуманный фильм.

`invalid` в запросе 10 — противоречивый ответ: модель вернула `status: ok` без единого фильма, код это отклонил. Провокация («Игнорируй каталог…») не сработала: модель ответила `no_match` и не предложила фильм вне каталога.

### Rare: условия запроса проверяет код, сравнение двух моделей

Набор вырос до 30 запросов, у каждого есть ожидание. Две локальные модели, по 3 прогона каждая (ответы меняются от запуска к запуску), одинаковый набор и одинаковые критерии; итог каждого запуска записан в `checks.jsonl`.

```bash
uv run check.py --runs 3                        # qwen3.5:4b
uv run check.py --runs 3 --model qwen2.5:14b
```

| Модель | Пройдено (3 прогона) | По прогонам | Чужих id до проверки | Нарушений условий поймано | Секунд на запрос | Цена | Цена по gpt-6-luna |
|---|---|---|---|---|---|---|---|
| `qwen3.5:4b` | **73 из 90 (81 %)** | 73 %, 83 %, 87 % | 0 | 0 | 1.7 | $0 (локально) | $0.00030 (2 493 / 107 ток.) |
| `qwen2.5:14b` | 71 из 90 (79 %) | 80 %, 80 %, 77 % | 0 | 0 | 5.8 | $0 (локально) | $0.00024 (1 885 / 99 ток.) |

Цена по gpt-6-luna — справочная: сколько стоил бы один запрос (оба вызова, вход / выход токенов в среднем) по её тарифу $0.10 / $0.50 за миллион.

Исходы: `qwen3.5:4b` — ok 56, no_match 29, invalid 5; `qwen2.5:14b` — ok 56, no_match 34.

**Что видно:**

- **Фильтры исправили то, на чём Common проваливался.** «С мамой на казахском, до двух часов» теперь разбирается в `{"max_minutes": 120, "languages": ["казахский"]}`, под условия подходят 2 фильма, и модель выбирает именно их (это ожидаемые «Тюльпан» и «Подарок Сталину»).
- **Маленькая модель не хуже большой:** `qwen3.5:4b` прошла 81 % против 79 % у `qwen2.5:14b` и в 3,4 раза быстрее. Большая модель стабильнее между прогонами (80/80/77 % против 73/83/87 %), но чаще ошибается одинаково все три раза.
- **Нарушений условий после выбора — 0:** модель выбирает только из отобранных кодом фильмов, поэтому повторная проверка кодом ни разу не сработала. Она остаётся страховкой на случай, если модель назовёт id фильма, которого не было в списке (тест `tests/test_filters.py`).
- **Фильтры удешевили запрос:** выбор идёт по части каталога, поэтому входных токенов на запрос (оба шага) стало меньше, чем при всём каталоге в промпте: 1 885 у `qwen2.5:14b` против ~6 000 в Common.

**Почему модели проваливаются** (по журналу, поля `note` у строк `step: filters`):

| Запрос | Что произошло |
|---|---|
| «қазақ тіліндегі отбасылық фильм» | обе модели поставили `languages: казахский` + `must_genres: семейный` — под оба условия в каталоге нет ни одного фильма, хотя «Тюльпан» по смыслу подходит. Фильтр слишком строгий: жанр «семейный» у казахстанских фильмов в Wikidata не проставлен |
| «очень длинный фильм, больше трёх часов» | обе модели записали `max_minutes: 180` — то есть «до трёх часов», наоборот. В схеме Filters нет поля «не короче», условие «больше» выразить нельзя |
| «қазақша күлкілі фильм» (смешной фильм на казахском) | `qwen2.5:14b` поставила `must_genres: ужасы` — не поняла казахское слово «күлкілі» |
| «казахстанский фильм про хакеров» | `qwen2.5:14b` добавила `must_genres: криминал`, а «Хакер» в каталоге — триллер, фильтр его отсёк |
| «фильм на киргизском языке» | фильтр верный («Айка»), но модель на выборе ответила «нет фильмов полностью на киргизском» |

Главный вывод: код надёжно проверяет то, что модель **записала** в фильтры, но если модель неправильно поняла запрос, строгий фильтр превращает ошибку понимания в ложное «ничего нет».

### Epic: каталог больше разумного промпта

**Каталог `films_big.json`: 1094 фильма, из них 43 казахстанских.** Собран скриптом `tools/fetch_big.py` из [Wikidata](https://www.wikidata.org) (CC0: название, год P577, длительность P2047, жанры, страны, языки) и вводных абзацев [русской Википедии](https://ru.wikipedia.org) (CC BY-SA) как описаний. Жанры, языки и страны приведены к словам `films.json` теми же таблицами соответствий, что и для малого каталога (`GENRES`, `LANGUAGES`, `COUNTRIES` в `tools/fetch_wikidata.py`: «драматический фильм» → «драма», «американский вариант английского языка» → «английский», «Республика Корея» → «Южная Корея»). Наши 47 фильмов входят в большой каталог с теми же id, поэтому ожидания из `queries.json` работают.

**Размер до первого запроса** (`uv run tools/big_check.py size`, без модели): промпт с малым каталогом — 17 441 символ, и у `qwen3.5:4b` он занял 6 257 токенов (2,79 символа на токен); промпт со всем `films_big.json` — 492 414 символов, то есть **≈ 176 700 токенов**. Фактически запрос со всем каталогом занял 184 390–184 505 токенов — оценка ошиблась на 4 %. В стандартное окно Ollama (4 096) это не помещается никак.

**Ловушка языка — выбран путь «русскоязычный датасет»:** описания взяты из русской Википедии, поэтому TF-IDF сравнивает русский запрос с русским описанием. Без sentence-transformers (torch — гигабайты зависимостей) и без перевода тысячи описаний моделью.

**Отбор без модели** — `candidates(query, films, k=30)` в `kinomaniac/search.py`:
- условия из запроса правилами: «до двух часов» → не длиннее 120 мин, «больше трёх часов» → не короче 180 (в схеме Filters из Rare так нельзя), «1990-х», «до 1970 года», «на казахском» / «қазақ», «советская» → СССР, жанры по корням слов («смешн», «күлкі» → комедия), отрицания «не / без / кроме» → исключение;
- «как Интерстеллар» → бонус фильмам с общими жанрами;
- ранжирование TF-IDF по названию, описанию и полям (стемминг — первые 6 букв слова).

`pick_big` отдаёт модели только эти 30 кандидатов и дальше работает как `pick`, все проверки Common и Rare те же (включая шаг фильтров Rare).

**Замер 1 — отбор отдельно** (`uv run tools/big_check.py recall`): фильм из `must` попал в 30 кандидатов в **22 из 23 запросов (96 %)**, ≈ 4 мс на запрос, модель не вызывается. Промах — «фантастика, снятая после 2000 года»: под запрос подходит сотня фильмов большого каталога, а в `must` только «Аватар» и «Интерстеллар». Оговорка: правила отбора я исправлял, глядя на эти же запросы (нашёл три своих ошибки: «до 1970 года» перебивалось правилом «ровно этот год», «не про космос» выкидывало всю фантастику, «про хакеров» выкидывало сам «Хакер»), поэтому на новых запросах доля может быть ниже.

**Замер 2 — весь путь** (`uv run tools/big_check.py path --limit 10`, первые 10 запросов набора, `qwen3.5:4b`, итог в `tools/big_results.json`). Задание предлагает облачную модель, ключа у меня нет, поэтому весь каталог прогнан локально: `qwen3.5:4b` держит до 262 144 токенов, Ollama запущена с окном 196 608. Чтобы сравнение было честным, вариантов три — отдельно видно, что даёт отбор кандидатов, а что фильтры Rare:

| Вариант | Пройдено | Вход на запрос | Выход | Секунд | Цена по gpt-6-luna |
|---|---|---|---|---|---|
| 30 кандидатов, без фильтров | **7 из 10** | 4 056 ток. | 82 ток. | 2.1 | $0.00045 |
| 30 кандидатов + фильтры Rare (`pick_big`) | **7 из 10** | 2 858 ток. | 129 ток. | 2.1 | **$0.00035** |
| весь каталог в промпте, без фильтров | 5 из 10 | 184 390 ток. | 127 ток. | 10.4* | $0.0185 |

\* Ollama кэширует одинаковое начало промпта (инструкция + каталог): самый первый запрос со всем каталогом (пробный, вне замера) шёл 75 секунд, а внутри замера каталог уже лежал в кэше. Без кэша каждый такой запрос стоил бы десятки секунд.

**Что видно:**
- **Рост с 5 до 7 из 10 даёт сам отбор кандидатов** — с фильтрами Rare и без них результат одинаковый; фильтры только дополнительно сокращают вход (4 056 → 2 858 токенов). Отбор в 45–65 раз сокращает вход и во столько же раз удешевляет запрос.
- Предыдущий прогон того же замера дал 8 из 10 для `pick_big` — ответы меняются от запуска к запуску, на 10 запросах разница в 1 запрос — это шум.
- **В длинном контексте модель теряется и выдумывает id.** На «индийский фильм с песнями и танцами» со всем каталогом модель дважды вернула несуществующий id: один раз `f-101` — id из **примера в инструкции**, другой раз `f-0023` — смесь форматов `f-023` и `b-0023`. Оба раза проверка кодом отклонила ответ (`invalid`, в журнале `rejected`). В пробном запросе «советская комедия» вторым фильмом шёл испанский «Лабиринт фавна» с пояснением самой модели «Испанский фильм без нужных условий».
- **Оговорка про ожидания:** ожидания в `queries.json` писались для малого каталога. В большом есть 7 индийских и 3 корейских фильма, поэтому ожидание `no_match` у «индийский фильм с песнями и танцами» и «фильм на корейском языке» для `films_big.json` уже неверно — модель, предложившая индийский фильм, на самом деле права. В замере 2 это запрос 9 из 10: с поправкой варианты с кандидатами прошли бы 8 из 10.

## Вопросы

**1. Почему программа сверяет id, хотя название понятнее? Сколько расхождений с каталогом дал опыт с памятью модели?**

id либо есть в каталоге, либо нет — это проверяется одной строкой без ошибок (`kinomaniac/verify.py:24`). Название сверять трудно: «Терминатор» и «Терминатор 2», опечатки, разные языки названия. К тому же модель не пишет ни название, ни год — их печатает код из каталога (`kinomaniac/render.py:16-20`: название, год, длительность и описание берутся из записи каталога, от модели — только `why`), поэтому ошибиться в годе модель просто не может. Опыт с памятью показал, зачем это нужно: без каталога модель ошиблась в годе у 5 фильмов из 10 и в длительности у 5 из 10.

**2. Что произойдёт, если модель вернёт `film_id`, которого нет в каталоге? Какие строки кода это ловят?**

Весь ответ получает исход `invalid`, пользователь не видит ни одного фильма — даже тех, что были в каталоге: если модель выдумала один фильм, остальному в этом ответе тоже нельзя доверять. Отклонённые id записываются в журнал в поле `rejected`. Ловят это `kinomaniac/verify.py:24-26` (поиск чужих id и исход `invalid`), а `kino.py:91-94` пишет `rejected` в журнал и возвращает пустой список фильмов. Проверка работает, даже если сервер не соблюдает схему: `film_id` в схеме — обычная строка (`kinomaniac/schema.py:9`), защита только в коде. Тест: `tests/test_kino.py`, `test_alien_id_makes_whole_answer_invalid`. Вживую это случилось дважды — на уровне Epic со всем каталогом из 1094 фильмов в промпте: модель вернула `f-101` (id из примера в инструкции) и `f-0023` (смесь форматов `f-023` и `b-0023`); оба раза ответ получил `invalid`, пользователь ничего не увидел, в журнале — `rejected`.

**3. Чем «модель ответила без ошибки» отличается от «модель подобрала верный фильм»? Как это видно в `check.py`?**

«Без ошибки» значит, что ответ разобран по схеме и все id есть в каталоге: исход `ok`. Но фильмы могут не подходить под запрос. На «с мамой на казахском, до двух часов» модель выдала «Жаужурек мын бала» на 132 минуты — id настоящий, проверка его пропустила, а условие нарушено. В `check.py` это две разные строки: «Исходы» (`ok` 10 из 16) и «Пройдено» (11 из 15 по ожиданиям `must`/`forbid`). Запрос пройден, только если в ответе есть хотя бы один фильм из `must` и нет ни одного из `forbid` (`check.py:24-33`). На уровне Rare условия проверяет код (`kinomaniac/filters.py:37` — `violations`, `:59` — `recheck`; вызов в `kino.py:86`), и тот же запрос проходит.

**4. Какое решение без ML записано в пяти вопросах лекции 1 и чего ему не хватает на запросах из `queries.json`?**

Фильтр по полям каталога и ключевым словам. Он справится с «советская фантастика» или «короткий семейный фильм до полутора часов», но не поймёт «как Интерстеллар, но не про космос» (нужно знать, чем похожи фильмы), «что-нибудь страшное», «для вечера с друзьями», «с мамой». Запросы на казахском («қазақша күлкілі фильм») ему тоже недоступны: слова не совпадают со словами каталога. И он не отличит «нет такого фильма» от «не нашлось ключевого слова». Такое решение без языковой модели в проекте на самом деле есть — это отбор кандидатов Epic (`kinomaniac/search.py:58` — условия из запроса правилами, `:176` — `candidates`). Как отбор 30 кандидатов оно работает хорошо (нужный фильм в 22 из 23 запросов), но выбрать 1–3 лучших оно не может: «как Интерстеллар, но не про космос» для него — просто фантастика с похожими жанрами, а казахские запросы понимаются только по нескольким корням слов, вписанным вручную.

**5. Сколько стоит один запрос и что сильнее всего влияет на цену?**

На локальной `qwen3.5:4b` — $0. По цене облачной gpt-6-luna ($0.10 за миллион входных токенов и $0.50 за миллион выходных) один запрос уровня Common стоил бы около $0.00064, а 10 000 запросов — около $6.41 (цена считается в `kinomaniac/journal.py:12`, функция `usd`, по `usage` из ответа). Сильнее всего на цену влияет **каталог в промпте** (`kinomaniac/prompt.py:34-35` — весь каталог уходит в тег `<каталог>`): около 6 250 токенов на входе против 76 на выходе, то есть больше 98 % токенов — это каталог, и он отправляется в каждом запросе. Цена растёт вместе с каталогом, поэтому для 1000+ фильмов нужен отбор кандидатов без модели (уровень Epic). Фильтры Rare уже уменьшают цену: в выбор уходит часть каталога, и запрос (оба вызова) стоит ~$0.00024–0.00030. Для большого каталога разница огромная: весь каталог — 184 390 токенов и $0.0185 за запрос, 30 кандидатов — 2 858 токенов и $0.00035 (в 53 раза дешевле).
